Inventory Management System

A real-time inventory tracker built with Next.js & Firebase. Thank you for your purchase! This guide walks you through setup, configuration, white-labeling and deployment.

Introduction

This is a production-ready inventory management app for small retail businesses. It tracks stock across two locations per item (for example front-of-store and back stockroom), monitors expiry dates, raises low-stock and expiring-soon flags, and keeps everything behind a secure phone one-time-password (OTP) login.

Data is stored in Cloud Firestore and syncs in real time — edit a quantity on one device and every other device updates instantly. It ships with a light/dark theme, an analytics dashboard, role-based access (Admin / Staff / Viewer), CSV import/export, an activity log, and PWA offline support. The whole app is white-label: you rebrand it from a single configuration file, no component code required.

💡 New here? Follow the sections in order: Requirements → Installation → Firebase setup → Configuration. You'll have a running app in about 15 minutes.

Installation

  1. Unzip & open the folder in your terminal. 
    cd inventory-management-nextjs-firebase
  2. Install dependencies. 
    npm install
  3. Create your environment file from the template. You'll fill in the values in the next section. 
    cp .env.example .env.local
  4. Set up Firebase (next section), then start the app: 
    npm run dev
    Open http://localhost:3000.

Firebase setup

The app needs a Firebase project with Phone Authentication and Cloud Firestore enabled.

  1. Create a project at console.firebase.google.com → "Add project".
  2. Enable Phone auth: Build → Authentication → Get started → Sign-in method → enable Phone. While testing, add a test phone number + code under "Phone numbers for testing".
  3. Create Firestore: Build → Firestore Database → Create database → start in production mode (the included rules replace the defaults).
  4. Register a Web app: Project settings (⚙️) → "Your apps" → Web (</>). Copy the config values into .env.local: 
    NEXT_PUBLIC_FIREBASE_API_KEY=...
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=your_project.firebaseapp.com
NEXT_PUBLIC_FIREBASE_PROJECT_ID=your_project_id
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET=your_project.appspot.com
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=...
NEXT_PUBLIC_FIREBASE_APP_ID=...
  5. Deploy the security rules shipped in firestore.rules: 
    npm install -g firebase-tools
firebase login
firebase use your_project_id
firebase deploy --only firestore:rules
  6. Add the login phone number. In Firestore, create collection phoneAuth with a document ID store and one field phone (string, E.164 format, e.g. +15551234567). This is the number the login screen texts the code to. The seed script can create it for you (see below).
⚠️ Note on the API key: the NEXT_PUBLIC_* Firebase keys are meant to be public — they ship in every Firebase web app. Your data is protected by security rules, not by hiding these keys. Never commit a service-account key, though (see Seeding).

Appearance & theme

The app ships with a full light + dark theme. A toggle in the header (and on the login screen) cycles System → Light → Dark; the choice is remembered per browser, and "System" follows the device setting. There is no flash of the wrong theme on load.

Changing the colours

All colours, spacing, radius and shadows are design tokens (CSS custom properties) defined once in src/styles/globals.css. To rebrand the palette, edit the tokens under :root (light) and :root[data-theme="dark"] (dark). The most common one:

:root {
  --primary: #3b6df6;        /* your brand colour   */
  --primary-hover: #2f5ae0;
  --header-bg: #141b2d;      /* top bar gradient    */
  /* …surfaces, text, radius, shadows… */
}

Every component reads these tokens, so one edit re-themes the whole app in both light and dark. Status colours (in-stock / low / expiring) come from a validated, colourblind-safe palette and are best left as-is.

💡 The heading/brand font is loaded as the --font-display CSS variable in _app.tsx — swap Calistoga for any next/font family to change it.

Roles & permissions

Every signed-in user has a role that controls what they can do. Roles are stored in a users collection (one document per user, keyed by their Firebase Auth UID) and enforced both in the UI and in the Firestore security rules.

The three built-in roles

CapabilityAdminStaffViewer
View inventory✅✅✅
View dashboard✅✅✅
Edit stock quantities✅✅—
Add products✅✅—
Delete products✅——
Manage users✅——

A user's role is shown as a badge in the header. Viewers get a read-only experience — the "Add" button and inline editing are hidden; only admins see the delete control.

Assigning a role to someone

  1. Have the person sign in once so Firebase creates their account.
  2. In the Firebase console → Authentication → Users, copy their User UID.
  3. In Firestore, create a document in the users collection with that UID as the document ID and a field role set to admin, staff or viewer. (The seed script can create your first admin — set ADMIN_UID and re-run npm run seed.)

Default role & customising

A signed-in user with no users document falls back to auth.defaultRole in app.config.ts (ships as viewer). For a single-operator shop where every login should have full access, set it to admin. To change what each role can do — or add new roles — edit src/utils/permissions.ts.

💡 Roles are enforced in firestore.rules too, so a viewer can't write data even via the API — not just in the UI.

Seeding demo data

To populate a fresh project with the sample catalogue so you can explore the app immediately:

  1. Generate a service-account key: Firebase console → Project settings → Service accounts → "Generate new private key".
  2. Save it outside the repo — e.g. ./secrets/service-account.json. The /secrets folder is git-ignored.
    🚫 Never commit a service-account key. It grants full admin access to your database and bypasses all security rules. Keep it out of version control.
  3. Point the app at it in .env.local: 
    GOOGLE_APPLICATION_CREDENTIALS=./secrets/service-account.json
# optional: also seed the login number
LOGIN_PHONE=+15551234567
# optional: grant admin to a UID (after signing in once)
ADMIN_UID=your_firebase_auth_uid
  4. Run the seeder. 
    npm run seed
    It writes the demo categories and products (and the login phone, if provided) to Firestore.

Security rules

The included firestore.rules enforce sensible, role-aware defaults:

  • phoneAuth — publicly readable (the login screen needs the number before sign-in) but never client-writable.
  • users — a user can read their own role document; roles are assigned from the console or an admin script, never from the client.
  • products & categories — readable by any signed-in user; writable only by admin/staff, and deletable only by admins. The rules read the caller's role from their users document, so the role model is enforced server-side, not just in the UI.
  • Everything else is denied by default.

Tighten further (per-user ownership, Firebase custom claims instead of a users collection, etc.) by editing firestore.rules and redeploying with firebase deploy --only firestore:rules.

Deployment

Option A — Vercel (recommended)

  1. Push the project to a GitHub/GitLab repo (make sure .env.local and any keys stay ignored).
  2. Import the repo at vercel.com — it auto-detects Next.js.
  3. Add the NEXT_PUBLIC_FIREBASE_* variables under Project → Settings → Environment Variables.
  4. Deploy. Add your production domain to Firebase → Authentication → Settings → Authorized domains.

Option B — any Node host

npm run build
npm start   # serves on port 3000 by default

In both cases, deploy your Firestore rules separately with the Firebase CLI (firebase deploy --only firestore:rules).

Install & offline (PWA)

The app is a Progressive Web App. On a deployed HTTPS site, browsers offer "Install app" / "Add to Home Screen", after which it launches in its own window like a native app. A service worker caches the app shell so it loads without a connection, and Firestore offline persistence keeps your inventory data readable offline — edits queue and sync automatically when the connection returns.

Make it yours

  • Edit public/manifest.json — set name, short_name, theme_color and the install icon (replace /logo.png with a 512×512 PNG).
  • The service worker is public/sw.js (registered automatically in production only).
⚠️ PWA install and the service worker require HTTPS (or localhost) and a production build — they're intentionally disabled in npm run dev.

Dashboard

The Dashboard (linked in the header) gives an at-a-glance view of inventory health, computed live from your Firestore data. Every role can view it.

What it shows

  • KPI cards — total items, categories, units in stock, "need to order", expiring soon and expired counts.
  • Stock status donut — In stock / Low / Out breakdown.
  • Expiry status donut — OK / Expiring soon / Expired / No expiry.
  • Units by category — a ranked bar chart of stock volume per category.
  • Needs attention — a prioritised list of the items that are low, out, expiring or expired.

The charts are lightweight, dependency-free SVG/CSS (no charting library to bloat your bundle) and use a colourblind-safe status palette with text labels on every series. The low-stock and "expiring soon" thresholds come straight from thresholds in app.config.ts, so the dashboard always matches your business rules.

Import & export

Export

Use Export on the main screen to download the entire inventory as a CSV, or Export CSV inside a category to download just the rows you're viewing (respecting the current search & filter). Opens in Excel, Google Sheets or Numbers.

Import

Editors (admin/staff) get an Import button that accepts a CSV file, shows a preview with row count and any warnings, then bulk-adds the products. Categories referenced in the file that don't exist yet are created automatically.

The CSV needs a header row. Required columns: category, flavor. Optional: front, back, expiryDate (column order doesn't matter):

category,flavor,front,back,expiryDate
Beverages,Cola 330ml,4,12,2026-09-15
Snacks,Salted Pretzels,10,20,n/a
💡 Exporting first is the easiest way to see the exact format before importing.

Activity log

Every add, stock edit, delete and import is recorded to an append-only activityLog collection with the actor's role and a timestamp. Admins get an Activity page (linked in the header) showing the latest 100 changes — useful for accountability when several staff share the app.

Entries are immutable by security rule (no client can edit or delete them), and only admins can read the history. Logging is best-effort: if it ever fails it never blocks the underlying action.

FAQ & troubleshooting

The login code never arrives

Check that Phone sign-in is enabled, the number in phoneAuth/store is in E.164 format (+ and country code), and — while testing — that you've added a test number under Authentication → Sign-in method. Real SMS on the free plan has daily quotas.

"Missing or insufficient permissions" in the console

Your Firestore rules aren't deployed, or you're not signed in. Deploy firestore.rules and confirm you completed the OTP login.

The app builds but shows no data

The project is empty — run npm run seed, or add a category and product from the UI.

reCAPTCHA errors on login

Add your domain (including localhost) to Firebase → Authentication → Settings → Authorized domains.

Can I change "Flavor" / "Front" / "Back" wording?

Yes — set labels.item, labels.front and labels.back in app.config.ts.
